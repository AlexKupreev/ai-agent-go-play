# Project review — errors, inconsistencies, and flexibility plan (2026-07-07)

Findings from a full pass over the documentation and code (all docs read end-to-end; cmd layer,
agent core, capability broker, sandbox, API layer, session store reviewed; `go build`, `go vet`,
and the full test suite pass). Two sections:

1. **Fixes** — errors and doc/code inconsistencies, ranked by damage.
2. **Flexibility** — proposals to make experiments possible without rebuild/redeployment,
   ranked by leverage.

Boxes are unchecked work, matching [`plan.md`](plan.md) conventions.

## 1. Fixes — errors and inconsistencies

### 1.1 Reference docs describe the old planner default (HIGH — documented command is broken)

The chat-planner feature (commit `a86d959`) inverted the default: deliberate planning +
critique are **ON** in `agent chat` and in `serve` session turns, disabled with `--no-plan` /
`--no-critique` / tuned with `--max-revisions` (`cmd/chat.go` init, `cmd/serve.go` init). The
reference docs still document an opt-in `--plan` flag:

- `README.md` §Ways to run — "`--plan` to run the planner per message".
- `docs/usage.md` §`agent chat` — "`./agent chat --plan` … off by default … experimental";
  §`agent serve` — "serve runs the executor directly (no interactive planner — there is no
  stdin to ask on)"; remote-mode note — "`--model` / `--tier` / `--plan` are local-mode only".
- `docs/environment.md` §Prompt customization — "`agent chat --plan`".

`./agent chat --plan` now fails with `unknown flag: --plan` (verified). The serve claims are
also false: the engine runs the deliberate pipeline headlessly, with planner `ask_user` routed
through the approval queue (`cmd/serve.go` `deliberateTurnRunner`).

**This is doubly damaging because `usage.md`/`environment.md` are embedded as the agent's
self-docs (`main.go` `//go:embed`) — the agent authoritatively misdescribes its own behavior
via `read_self_docs`.**

- [x] Rewrite the `agent chat` / `agent serve` sections of `usage.md` around the deliberate
      default (`--no-plan`, `--no-critique`, `--max-revisions`; `/reload` is a no-op in plan
      mode because prompts are re-read each turn). **Done 2026-07-07.**
- [x] Fix `README.md` §Ways to run and the command-reference table in `usage.md`. **Done.**
- [x] Fix `environment.md` (`chat --plan` → the deliberate default) and the `PLANNER.md` row.
      **Done.**

- [x] Document all of the above in `usage.md` + `environment.md` (prompt-file table, chat

### 1.4 Unbounded memory growth in a long-lived `serve` (MEDIUM — code, not docs)

- `Engine.runs` is never pruned (`internal/api/engine.go`), and each run's `Hub` retains its
  full event history for replay (`internal/api/hub.go`) — including request/response payloads.
  Every chat/Telegram turn is a run, so a weeks-long `serve` on the ~2 GB target box
  accumulates all of it.
- `Engine.sessLocks` also grows one mutex per session forever.

- [x] Evict finished runs (e.g. keep the last N=100 or a TTL after `EndedAt`); drop the hub
      history on eviction. Free a session's lock when the session is deleted.
      **Done:** `Engine.pruneFinished` (cap `maxFinishedRuns = 100`, oldest-finished evicted
      after each run completes; running runs never evicted; eviction unreferences the run and
      its hub history — the on-disk transcript keeps the durable record), and `CloseSession`
      now deletes the session's turn-lock entry. Tests: `TestFinishedRunEviction`,
      `TestCloseSessionFreesTurnLock`.

and even explicit `--context-file`s (`cmd/prompts.go` `loadPrompts`, `cmd/agents.go`
`loadAgentCatalog`).

- [x] Correct the flag help string. **Done 2026-07-07** (`cmd/root.go` now lists all prompt

## 2. Flexibility — experiments without redeployment

Already good (keep as-is): hot-reloadable `SYSTEM.md`/`AGENTS.md`/`PLANNER.md`/`CRITIC.md`,
`agents/*.md` sub-agent types with per-type `model:` override, `agent eval` variants, engine
aliases, per-`--config-dir` independent agents.

The gaps, in leverage order:

### 2.1 Provider base URL + second adapter (HIGHEST leverage, ~10 lines for the first step)

`openaiprovider.New(cfg.OpenAIKey)` pins the agent to api.openai.com — there is no `base_url`
anywhere in the tree. On a 2 GB box wanting local-model experiments this is the single biggest
lock-in.

- [x] Add config key `openai_base_url` (+ env `AI_AGENT_OPENAI_BASE_URL`), passed via
      `option.WithBaseURL` in `internal/provider/openai`. Instantly opens llama.cpp / Ollama /
      vLLM / OpenRouter / any OpenAI-compatible endpoint. **Done 2026-07-07:**
      `openai.New(apiKey, baseURL)`; `Config.OpenAIBaseURL` + `resolveOpenAIBaseURL`; a single
      `newProvider(cfg)` construction point routes all four callers (run/chat/serve/eval); a
      `config set-base-url` setter; documented in `usage.md` + `environment.md`. Tests:
      `TestResolveOpenAIBaseURL`.
- [ ] (Later) `provider` config key (`openai|anthropic|…`) selecting an adapter behind the
      existing `provider.Provider` port; lets `eval` sweep across providers. The port already
      isolates the SDK, so this is additive. `newProvider(cfg)` is now the one seam to extend.

### 2.2 Per-run / per-turn overrides over the API (HIGH)

`serve` fixes model and tier at process start; `POST /runs` accepts only `{task}`; `/reload`
re-reads prompts but not config. Restarting the engine is currently the only way to change
model or tier.

- [x] Accept optional `model` / `tier` in `POST /runs` and `POST /sessions/{id}/turns` (per-turn).
      **Done 2026-07-07 (Phase 1):** `api.RunOptions{Model,Tier}` threaded through the
      `Runner`/`TurnRunner` seam (struct, so future per-role models are field additions); cmd's
      `resolveOpts` applies the model default and **clamps** tier via `capability.ClampTier` (the
      `serve --tier` flag is a hard ceiling); an invalid tier fails the run. `agent client
      --model/--tier` passes through. ~8 test fakes updated. Tests: `TestClampTier`,
      `TestResolveOpts`, `TestHTTP_StartRunPassesOptions`; verified live (clamp + reject).
- [x] **Phase 2:** per-**session** sticky model/tier. **Done 2026-07-08:** `session.Session.{Model,Tier}`
      (also on the listing `Info`, exported `ToInfo`); `Engine.StartSession(RunOptions)` persists the
      initial stickies and a new `Engine.UpdateSession(id, model, tier *string)` changes them live
      (per-field pointer semantics — a nil field is untouched, an empty string clears). `POST /sessions`
      takes `{model?,tier?}`, `PATCH /sessions/{id}` updates them (400 on a bad tier, 404 unknown); the
      tier is validated syntactically at the transport boundary (`validateTierOpt`) while clamping stays
      per-turn in `resolveOpts`. `PostTurn` merges **turn override > session-stored > serve default**.
      `Client.StartSession(opts)` + `Client.UpdateSession`; remote `agent chat` `/model`/`/tier` (and
      `--model`/`--tier` at launch) drive the PATCH. Tests: `TestFileStore_StickyModelTier`,
      `TestEngine_SessionStickyModelTier`, `TestEngine_UpdateSessionUnknown`,
      `TestHTTP_SessionStickyOverrides`; live-verified over `serve` (POST/PATCH/GET, partial update,
      400/404). Per-role models (planner≠executor≠critic) remain a later `RunOptions` field addition.
- [ ] And/or extend `POST /reload` to also re-read `config.json` defaults (model, tier). *(Optional;
      Phase 2's PATCH covers the live-change need for sessions.)*
- [x] Chat REPL: live `/model [id]` and `/tier [t]` commands, mirroring `/verbose`. **Done
      2026-07-07:** no-arg shows current; setting rebuilds the executor in place (bare chat,
      carrying the conversation) or takes effect next turn (deliberate mode). Test:
      `TestModelLabel`.

## 3. Session & run lifecycle — archive and diagnostics (added 2026-07-07)

Follow-ups to §1.4. Context: after run eviction landed, the only *irreversible* path left is
closing a session (`/end`, `DELETE /sessions/{id}` → `os.Remove`); everything else already has
a durable disk record (per-run transcripts under `<runs-dir>/<run-id>/`, the session store,
the process-wide `audit.jsonl`).

### 3.1 Archive sessions on close instead of deleting (MEDIUM)

`Engine.CloseSession` / `session.FileStore.Delete` remove the conversation file permanently —
one `/end` keystroke in Telegram destroys the history. Everything needed to resume is in that
one file (the executor is rebuilt from history each turn), so an archived session is fully
restorable by construction.

- [x] `FileStore`: move `sessions/<id>.json` → `sessions/archive/<id>.json` on delete
      (`List` already skips subdirectories). Keep `Delete`'s signature; add `Purge` for true
      removal and `Restore` to bring an archived session back. **Done 2026-07-07.** Tests:
      `TestFileStore_DeleteArchivesAndRestore`, `TestFileStore_Purge`.
- [x] The session's scratch dir (`session-scratch/<id>/`) is reaped on close — via an engine
      `SetSessionCloseHook` seam that `cmd/serve.go` wires to `os.RemoveAll` the scratch dir
      (scratch is large + re-derivable, so it's removed, not archived). Closes §1.2's "no
      reaper" item. Test: `TestCloseSessionFiresHook`.
- [x] Document the restore path (move the file back → `chat --addr --session <id>`), and
      update `environment.md`'s "deleting them resets the corresponding state" note. **Done**
      (usage.md sessions section, environment.md files-on-disk table + caveat, api-transport.md).

### 3.2 Persist RunInfo at completion (MEDIUM)

An evicted (or restart-lost) run's metadata — task, state, final result, usage, timings —
lives only in memory; the transcript has the raw events but nothing reads them back.

- [x] Write `<runs-dir>/<run-id>/info.json` (the `RunInfo` JSON) when a run reaches its
      terminal state. **Done 2026-07-07** via an injectable `api.RunStore` (Save/Load) on the
      engine; `cmd/runstore.go`'s `fileRunStore` writes it atomically next to the transcript
      (with a path-traversal guard on the run id). Saved *before* pruning, so an
      immediately-evicted run is still persisted. Test: `TestRunStoreSurvivesEviction`.
- [x] (Optional) `GET /runs/{id}` falls back to reading `info.json` for evicted ids. **Done** —
      `RunStatus` calls `RunStore.Load` when the live map misses; live SSE replay stays
      memory-only (an evicted run's `Subscribe` still 404s, documented).

### 3.3 Sessions/runs in RAM — assessment + knobs (LOW; mostly already fine)

Assessed 2026-07-07: session histories are **not** cached in RAM — `FileStore` reads the JSON
per turn and the engine drops it after; `sessLocks` is one mutex per *active* session (freed
on close since §1.4). The remaining RAM holders are the retained finished runs' hub histories
(bounded at `maxFinishedRuns = 100` since §1.4; wire events carry text/tool results but not
full message payloads) and local `chat`'s in-process conversation (inherent to bare-chat mode).

- [x] Make `maxFinishedRuns` a config key (folded into §2.4's `limits` section) so a small box
      can run tighter (e.g. 20) without a rebuild. **Done 2026-07-07** (`max_finished_runs` →
      `Engine.SetMaxFinishedRuns`).
- [ ] (Only if it ever bites) cap a single hub's history length — one pathological run with
      huge tool results can still hold a large history while retained; cap replay to the last
      N events or the last M bytes.

### 3.4 Disk-usage diagnostics in the `status` tool (MEDIUM)

The agent can see host disk free/total (`hoststat`), but not what *its own state* occupies —
it cannot answer "how much space are my sessions/transcripts taking?" or notice that
`runs/` (no reaper, by design) is what's eating the disk.

- [x] Extend `StatusDeps`/the `status` tool with an "agent state on disk" section: per store
      (transcripts `runs/`, sessions incl. archive, `session-scratch/`, `tools.json`,
      `memory.json`, `audit.jsonl`) report entry count + total bytes. **Done 2026-07-07** —
      `StateDir` + `diskUsage` (best-effort walk, `maxStateWalkFiles` budget, `≥` on a capped
      total). Tests: `TestStatusTool_StateOnDisk`, `TestStatusTool_NoStateDirs`.
- [x] The cmd layer passes the resolved paths into `ExecutorConfig.StatusDirs` → `StatusDeps`
      (`cmd`'s `agentStateDirs`); `internal/tools` resolves no paths itself. **Done** (wired in
      run/chat/serve/eval).
- [x] Mention the new section in the tool description and in `usage.md` §Self-status. **Done.**
